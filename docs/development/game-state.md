# 游戏实体与关卡状态（首版设计稿）

日期：2026-10-27。依据[六关通用规范](../levels/00-common.md)、各关规则及对话确认的服务器裁决、匿名扫码和统一时间轴。本文是研发基线，不代表代码或实测已完成。旧关卡文档中客户端上报位置和判定的描述，以本稿的服务器模拟为准；具体数值以实机试玩调整。

## 1. 范围和约定

一个服务进程管理 Demo 房间，状态放内存；不建数据库、不做账号体系。房间、玩家、对局、当前关卡是逻辑分组，不要求分别建类。全部示例都是 JSON 可表示的数据，服务端可用普通对象或 Map 存储。

- 字段类型：`string` 字符串、`number` 数字、`boolean` 布尔值、`null` 无值；`Record<ID, T>` 是以 ID 为键的对象。
- 时间字段 `*At` 是服务端 Unix 毫秒时间戳；持续时间字段 `*Ms` 是毫秒。服务端以单调时钟管理计时，向客户端转换成可比较的服务端时间。客户端估算时间只供显示，不用于裁决。
- 地图单位为米、Y 轴向上。标准平台中心 `(0, 0, 0)`，X 从西向东，Z 从北向南；`col` 西→东、`row` 北→南，各为 0–19，普通地砖编号 `row * 20 + col`。桂市另用 `row * 10 + col`，依固定台阶布局。
- `playerId`、`roomId`、`matchId`、物品 ID 由服务端生成。昵称允许重复，只是显示名；在同一浏览器使用 `localStorage` 保存昵称、玩家 ID、恢复凭证、最近房间标识。凭证只返回本人，不进入房间广播或日志。
- `null` 表示尚未产生或不适用，不用 0 充当时间或 ID。ID 和时间在同一局内保持稳定；随机决策由服务器生成并同步结果，不要求两端独立复现随机数。

## 2. 房间 Room

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | string | 房间标识，生成扫码链接时使用 |
| `players` | Record<playerId, Player> | 玩家及观众；断线不立即删除 |
| `match` | Match \| null | 当前对局；未开始为 null |

房间是否等待或进行中可由 `match` 与阶段推导，不单独保存一份。房主不是玩家：管理端创建房间并发送控制命令。房间链接不能取得管理端控制权；管理端凭证/连接存在服务端连接层，不放入公开快照。首版默认一间房，玩家上限 32；开局后新加入者作为观众。

## 3. 玩家 Player

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | string | 稳定玩家标识，重连不变 |
| `name` | string | 玩家输入的昵称 |
| `color` | string | 玩家选择的身体颜色 |
| `connected` | boolean | 当前是否连接 |
| `status` | `waiting` \| `playing` \| `qualified` \| `eliminated` \| `spectating` | 入场、参赛、提前晋级、淘汰、非参赛观众；晋级结算后下一关重置为 playing |
| `avatar` | Avatar \| null | 场上角色状态；无角色时为 null |

`qualified` 主要用于酒市达标后立即退场；其他关可在结算时确定晋级。淘汰玩家保留 `eliminated` 并使用观战镜头；开局后新加入者为 `spectating`。房间内按玩家加入时的插入顺序保存并用于稳定兜底排序，无须额外排序字段；如果实现容器不保证顺序，则须显式保存入场顺序。`connected` 只表示连接，与参赛资格分开。

服务端额外保存 `playerId → 恢复凭证` 的私有映射；不属于公共 Player。昵称重复允许入场，身份以 ID 区分。localStorage 因清除数据、换设备、换浏览器或站点而不可用时作为新玩家进入。

### Avatar

| 字段 | 类型 | 含义 |
|---|---|---|
| `position` | `{x, y, z}` | 角色中心的权威坐标 |
| `velocity` | `{x, y, z}` | 权威速度，单位米/秒 |
| `facing` | number | 朝向角，弧度；绕 Y 轴，0 朝北（−Z），正角转向东（+X） |
| `grounded` | boolean | 是否接地；决定起跳及踩砖 |
| `jumpHeld` | boolean | 服务器当前采纳的跳跃按住状态，支持短跳/长跳 |

模型动作如待机、跑步通常由速度、接地和玩家状态推导，不再存一份易失同步的动画状态。客户端自行保存本地预测/插值与未确认输入历史，不作为服务器公共状态。服务器可另外维护输入序号、上次输入时间及跳跃沿等内部运行数据；权威位置快照要携带对应的已处理输入序号，以便客户端校正，不能把 socket ID 当玩家 ID。

## 4. 对局 Match 和统一时间轴

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | string | 本局唯一 ID，重开生成新值 |
| `phase` | `intro` \| `card` \| `countdown` \| `playing` \| `result` \| `transition` \| `ending` \| `finished` | 由服务端控制；可选片头用 intro |
| `phaseId` | number | 每次阶段转换递增；用于忽略过期消息 |
| `phaseEndsAt` | number \| null | 当前阶段截止时间；finished 为 null；特殊阶段可提前结束 |
| `transitionId` | `normal` \| `wind` \| `rebirth` \| null | 仅 transition 时标识普通切关、风起或再生；ending 是独立阶段 |
| `level` | LevelState \| null | 当前关及动态数据；intro/finished 可以为空，过场可保留上一关用于画面 |
| `participants` | string[] | 本局已参赛玩家 ID，保留淘汰者以供结局名单 |
| `results` | LevelResult[] | 已结束关卡的结果；客户端展示由此得到名单 |
| `championId` | string \| null | 产生冠军后设置 |

`phase` 是唯一全局阶段来源，不在 LevelState 再存一份全局 phase。默认卡片 6 秒、倒计时 3 秒、结果 5 秒、普通过场 2 秒、风起 8 秒、再生 6 秒，结局约 45–60 秒；时间由服务端确定。媒体本地播放进度不写入 Match，也不决定阶段推进。重连时按当前阶段和截止时间显示，视频可从任意位置或占位开始，到服务端截止时切换。

### LevelResult

`{ levelId, qualifiedIds, eliminatedIds, scores, reason }`。

- `qualifiedIds`、`eliminatedIds` 为玩家 ID 数组；`scores` 是 `Record<playerId, number>`，没有可比较分数的关可为空对象；`reason` 为 `normal` 或 `host_skip`。最终冠军存 `championId`。
- 开局前仅剩 1 人直接产生冠军；房主跳关保留当前已经发生的淘汰，仍有资格者进入下一关。零人、并列和人工直接结局采用[研发方案](multiplayer-architecture.md)第 5、8 节的首轮兜底，作为待试玩确认的建议。
- 断线不会使时间轴暂停；世界继续模拟，重连时如果已经淘汰则观战。服务进程重启会丢失本局。大厅离线席位和游戏中断线超时策略见研发方案第 9 节。

## 5. 关卡配置与运行状态

配置保存不随本局变化的参数、布局及资源引用，随程序或 JSON 文件发布；运行状态由服务器创建并修改。配置变更先在所有客户端加载同版本；Demo 不支持一局中更改配置。客户端只读状态，服务器生成变化和结算。

配置公共字段建议为 `id`、`name`、`durationMs`、`advanceRatio`（不适用时 null）、`rules`（各关参数）、`layout`（地面、出生点、区域和终点）。关卡介绍文字与资源路径可以放配置，不放运行状态。下表的具体数值都为初始值，需真机调整。

| 关卡 ID | 配置中关键参数 |
|---|---|
| `01-jinshi` | 60 秒；20×20、1 米地砖；≥8 人四队、4–7 人两队、少于 4 人个人赛 |
| `02-dengshi` | 每题作答 10 秒、塌陷 2 秒、复原 2 秒；最多 5 题；晋级比例 0.7；答案区宽 6/8/6 米 |
| `03-qibaoshi` | 60 秒；晋级比例 0.65；拾取半径 0.8 米；每秒在场人数×0.5 张；下落约 2 秒、落地后保留 8 秒 |
| `04-shisan` | 最长 60 秒；晋级比例 0.6；开局保护 1 秒，接地踩踏后 0.6 秒消失 |
| `05-jiushi` | 最长 60 秒；晋级比例 0.6；3 袋达标；拾取半径 0.8 米、交付半径 1.5 米；拾取后 1 秒补货；初始地面粮袋数为在场人数×2，最少 6 |
| `06-guishi` | 最长 60 秒；20 级×10 块；踩踏 0.8 秒后消失；开局 3 秒后逐排塌落、间隔 1.5 秒逐渐缩至 0.6 秒；3 处缺口、终点半径 1 米 |

灯市题库配置包含题目稳定 ID、题干、3 个选项、正确选项和来源。服务端保留正确答案，公开快照在锁定前只发题干和选项，锁定判定后再发布正确选项和结果。首版以服务器发出的实际物品与题目为准，不要求客户端通过随机种子自行重建。

### 通用关卡运行状态 LevelState

```ts
type LevelState = {
  id: LevelId;                // 六个固定关卡 ID
  startedAt: number | null;  // playing 实际开始时刻，之前为 null
  targetCount: number | null; // 目标晋级数；锦市按队伍结算、桂市冠军制可为 null
  data: JinshiState | DengshiState | QibaoshiState | ShisanState | JiushiState | GuishiState;
};
```

`id` 决定 `data` 的具体类型；生产代码应用 TypeScript 联合类型约束它们匹配。运行中 `data` 只包含当前关，关卡结束后保留 `LevelResult`。数组内容可以是对象而非压缩形式，先以易调试为主。服务器内部可保存额外计时、随机生成和比较用数据；以下定义是可序列化的游戏状态基线，不要求每项都频繁广播。

## 6. 六关的 data 字段

### 锦市 JinshiState

| 字段 | 类型 | 含义 |
|---|---|---|
| `teams` | `{id, playerIds, tileCount, reachedAt}[]` | 队伍或个人赛的单人队；格数及达到当前格数的时间 |
| `tiles` | `(string \| null)[]` | 长度 400；每格为队伍 ID 或未染色 null |

服务端根据脚下地砖染色，覆盖时同步维护双方 tileCount 和对应 reachedAt。结束时最少队淘汰；同分依据原规则的达到最终数量时间，再同分按入场顺序稳定决定。团队颜色和队员可从 teams 推导，不在 Player 再存一份 teamId。

### 灯市 DengshiState

| 字段 | 类型 | 含义 |
|---|---|---|
| `questionIndex` | number | 当前题序，从 0 开始 |
| `question` | `{id, text, options}` \| null | 当前公开题目，options 为 A/B/C 三项 |
| `questionPhase` | `answering` \| `revealing` \| `restoring` | 当前题子阶段；锁定为 answering→revealing 的瞬间 |
| `questionPhaseEndsAt` | number | 当前子阶段截止时间 |
| `answer` | `A` \| `B` \| `C` \| null | 判定前 null，公布后为正确选项 |
| `roundResult` | `{void, eliminatedIds, savedIds}` \| null | 全错作废、淘汰和补足晋级玩家，下一题清空 |

未公开题目顺序、正确答案和锁定时每个玩家的位置及距离保存在服务器内部，以便判定，不发送给客户端。服务器固定时刻使用角色中心水平位置，即使空中也可锁定；作废或补足规则见关卡文档。

### 七宝市 QibaoshiState

| 字段 | 类型 | 含义 |
|---|---|---|
| `items` | `Record<itemId, {x, z, spawnedAt, landsAt, expiresAt}>` | 场上尚未拾取/过期的交子，落地前不可拾取 |
| `scores` | `Record<playerId, {count, reachedAt}>` | 当前拾取数量及达到该数量的时刻；初始为 0 和 null |

服务端定时创建、落地、移除并裁决拾取；每个 ID 最多给一人。已拾取物品从 `items` 移除，变化事件通知客户端；重连快照只需当前仍存在的物品。相同分数按 reachedAt 排名，仍并列时按入场顺序。

### 市散 ShisanState

| 字段 | 类型 | 含义 |
|---|---|---|
| `tiles` | `{disappearsAt: number \| null}[]` | 400 格；null 为完整，否则为预定消失时间；当前是否消失可按时间推导 |
| `fellAt` | `Record<playerId, number>` | 本关掉落时刻，供全员掉落和并列兜底 |

开始后前 1 秒保护；保护结束要检测已站立的地砖。仅接地触发，不因空中经过触发；掉落和淘汰由服务器判定。

### 酒市 JiushiState

| 字段 | 类型 | 含义 |
|---|---|---|
| `sacks` | `Record<itemId, {x, z, carrierId}>` | 粮袋位置及携带者；`carrierId: null` 表示在地面上 |
| `scores` | `Record<playerId, {count, reachedAt}>` | 每人已交付袋数及达到当前数量的时间 |
| `qualifiedIds` | string[] | 已达标并立即晋级的玩家，按达标顺序排列 |

每人最多携带一袋；持有关系从 sacks 的 carrierId 推导。服务器内部记录拾取后待补货的时间与位置、掉落归还所需原位置；交付成功移除对应粮袋并加一次分。四角交付区为固定配置。累计交付数可从 scores 推导，用于酒坊表现。

### 桂市 GuishiState

| 字段 | 类型 | 含义 |
|---|---|---|
| `tiles` | `{gap: boolean, disappearsAt: number \| null}[]` | 200 块台阶；gap 为初始缺口，非缺口在踩踏或逐排塌落时设置消失时间 |
| `fellAt` | `Record<playerId, number>` | 记录掉落时刻；若全部掉落用于决定冠军 |
| `winnerId` | string \| null | 到达终点或兜底确定的冠军，关卡结束后写入 Match.championId |

逐排塌落时间在服务端初始化或运行时确定；与踩踏时间取较早者。到终点由服务器判定，全掉落按最后掉落者，超时等兜底见研发方案。地图进度可以依据服务器坐标和配置计算，不再维护一份可能不一致的距离排名。

## 7. 快照与增量

公开房间快照形如 `{ serverTime, room: { id, players, match }, revision }`，仅发给房间内客户端；连接本人另收自己的 `playerId`，首次入场或恢复时通过私人响应接收恢复凭证。`revision` 是本房间内权威游戏状态版本，状态变化后递增；客户端检测缺口时请求快照。位置为高频状态，独立携带服务器 tick 和本人已处理输入序号；不因丢弃位置包误判关键事件 revision 缺口。快照生成和 revision 读取须在同一状态点，后续事件按 revision 顺序应用；快照期间到达的事件按版本缓冲或重取，避免覆盖新事件。

- **入场/重连**：完整快照，包括当前阶段截止时间、玩家、当前关状态和成绩；不含恢复凭证、房主凭证或灯市未揭晓答案。
- **正常游玩**：定期广播角色位置；地砖、物品、计分和阶段等发送有版本的变化事件，不每帧广播完整 400 格或整个房间。
- **恢复当前过场**：显示剩余时间并可从任意位置播视频或显示占位；到服务端截止时间即切换。
- **局外身份**：localStorage 保存最近房间、昵称、玩家 ID 和恢复凭证；房间已结束/不存在时保留昵称预填并引导加入新房间。局中仍在线但淘汰的玩家观战。

## 8. 需要实施时验证的事项

- 模拟步长 30/60Hz、输入采样与服务器消费对应关系、预测重放和广播频率必须先通过联机原型验证；配置值不是性能保证。
- 服务端掉线判定与恢复窗口需与现场实际网络验证，避免偶发波动误淘汰；不存在服务器崩溃后的对局恢复。
- 地砖消失与客户端预测可能冲突，采用服务器状态校正；灯市锁定和抢物品以服务端位置/时间为准。
- 美术资源尺寸、手机过场播放与占位内容仍存在文档冲突，待 U01 统一，不影响上述统一阶段控制。
