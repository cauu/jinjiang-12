# 多人联机研发方案（讨论稿）

日期：2026-10-27。目标是在黑客松时间内做出能完成整局的多人游戏。本文是实现建议，数值和接口仍需首轮联调验证；它将原设计中“客户端自报判定”的方案调整为服务器模拟和裁决。视觉与视频方案的现有冲突仍需单独确定。

## 1. 目标和取舍

- 单场一间房，最多 32 名玩家；手机横屏操作，大屏观战兼房主；六关按既定顺序进行。房间作为隔离单位设计，但首版只部署一个进程、运行一个房间，不承诺多房间运营。
- 服务器负责玩家运动的权威状态、地面和物品、计时、淘汰、排名与冠军。客户端发送操作输入并渲染；客户端的预测只影响视觉，不能决定结果。
- 不做账号、数据库、付费、复杂物理、反作弊或水平扩容。玩家之间提供基础阻挡碰撞。先保证单局、短暂断线恢复、房主兜底、现场重开可用。
- 单进程内存保存对局；进程崩溃或重启会丢失本局。现场需保留重启、重新扫码和房主跳关预案。游戏中可断线重连是对旧设计“不做断线重连”的主动调整，优先覆盖手机网络波动。

## 2. 方案选择

建议使用 TypeScript、Node.js、Socket.IO 和 Three.js，前后端共享纯 TypeScript 的移动计算、协议类型和常量；一个服务同时提供静态网页、HTTP 健康检查和实时连接。Socket.IO 是建立在多种传输之上的协议，客户端需使用对应库，不是原生 WebSocket 协议；它提供心跳、自动重连和 HTTP long-polling 兜底。房间是服务器侧广播分组，游戏房间状态仍由我们维护。

比较：

| 方案 | 适用性 | 本项目判断 |
|---|---|---|
| 原生 WebSocket / ws | 依赖少、完全可控 | 房间、心跳、重连及恢复都要自己实现，开发负担更大 |
| Socket.IO | 房间广播、重连与回调简单，Web 技术栈熟悉 | 推荐；需要自行定义游戏状态、模拟及断线恢复 |
| Colyseus | 专门的游戏房间、状态同步、预测工具 | 可行；其状态模型和框架学习、集成有成本。若团队已有经验，可在 M0 实测后替换；不在本方案中混用两套实时框架 |

参考：[Socket.IO 介绍](https://socket.io/docs/v4/)、[房间](https://socket.io/docs/v4/rooms/)、[消息送达保证](https://socket.io/docs/v4/delivery-guarantees/)、[Colyseus 固定步长与输入](https://docs.colyseus.io/netcode/server-input)、[客户端预测与校正](https://docs.colyseus.io/netcode/client-prediction)。这些资料说明的是框架能力，不构成本项目 32 人性能保证。

## 3. 模块边界

```text
手机：输入 / 预测 / 画面 / UI ─┐
大屏：画面 / 房主控制         ├── Socket.IO ── 房间与连接
                              │                 ├── 对局流程与计时
                              │                 ├── 固定步长运动模拟
                              │                 ├── 六关规则与结算
                              │                 └── 快照与事件广播
                              └── HTTP：页面、资源、健康检查
                  前后端共用：协议、坐标与运动规则
```

服务端的房间模块持有状态；流程模块唯一负责阶段转换；关卡规则通过初始化、每步更新、结算三个入口处理，不能自行更改全局阶段。传输层只解析和发送消息，不写玩法规则。客户端网络层把快照和事件转换成画面状态，渲染层不参与裁决。先按职责组织代码，不预设复杂框架或微服务。

## 4. 核心实体

| 实体 | 关键字段及责任 |
|---|---|
| Room | `roomId`、`joinCode`、`status`、`players`、`match`、`hostSession`；隔离连接和对局。房间码用于加入，不是房主凭证。 |
| Player | `playerId`、`name`、`color`、`connectionStatus`、`participation`（等待/参赛/淘汰/观战）、`teamId`、`reconnectToken`；身份与 socket 连接分离。 |
| Match | `matchId`、`phase`、`phaseId`、`levelId`、`phaseStartedAt`、`phaseEndsAt`、`participants`、`result`；由服务器单一时钟推进。每次重新开始创建新 `matchId`。 |
| Avatar | `position`、`velocity`、`facing`、`grounded`、`lastProcessedInputSeq`；由服务器固定步长模拟；活动玩家之间按球形体积阻挡，客户端进行近似预测并接受服务端校正。 |
| LevelState | 关卡实例、随机种子、目标晋级人数，以及本关砖块、物品、题目或进度；只存当前关必要状态。 |
| Tile | 网格坐标、归属队伍、状态及消失时刻；用数组或紧凑表示，变化批量广播。 |
| Item | `itemId`、类型、位置、可拾取/已领取/消失状态、所属玩家或消失时间；服务器串行裁决。 |
| Result | 每人本关成绩、排名、晋级状态及最终冠军；支持大屏展示和断线快照。 |

房主是一种经过授权的连接角色，不占玩家席位。房间码和仅现场管理者持有的随机房主凭证分开；不能因拥有扫码链接就取得跳关权限。凭证不放在公共扫码 URL 中。会话令牌只在自己的客户端保存及发送，快照绝不广播这些令牌。

## 5. 游戏链路和阶段

`LOBBY → INTRO(可选) → CARD → COUNTDOWN → PLAYING → RESULT → TRANSITION → 下一关 CARD → ENDING → FINISHED`。

- 房主打开大屏，用管理凭证创建/接管房间；大屏显示玩家加入地址及二维码。玩家输入名字和颜色，服务端确认席位后发放玩家 ID 和随机恢复令牌；开始后新加入者作为观众，不挤占参赛席位。
- 房主开始，服务端冻结参赛名单，生成关卡实例与出生点，按服务端时间驱动卡片、倒数、游戏和结算。每次转换递增 `phaseId`，任何客户端的动画结束或视频播放失败都不能控制流程。过场按固定截止时间推进，播放失败显示占位卡。
- 倒数期间允许移动但不触发计分/踩砖；PLAYING 开始时处理脚下地砖。每关结束先冻结输入效果、做一次服务端结算，再广播结果。市散开局保护结束时检查所有站立玩家脚下的砖。
- 前五关结算后如仅剩一人，直接产生冠军；桂市首位合法抵达终点者夺冠。零人、全掉落、并列、跳关按第 8 节处理。结局统一由服务器发送冠军和名单；所有终端以此显示。
- 手动跳关和直接结局只允许房主使用，携带 `matchId`、`phaseId` 与幂等 `requestId`。跳关对当前已完成的淘汰与成绩保留，以当下仍有资格的参赛者晋级；若零人则按第 8 节兜底。直接结局按当前关已有成绩排名选冠军，无法比较时按稳定入场顺序选出并明确标记为人工结局。服务端转换阶段后旧指令失效，重复请求返回原结果。
- FINISHED 时房主可重置房间，保留在线玩家但创建新的 `matchId`；清除旧关卡、计分、计时器和待处理输入。

## 6. 网络协议草案

JSON 为首版格式。所有客户端请求采用 `{requestId, matchId?, phaseId?, payload}`，确认回调返回 `{ok, code, data?}`；公开事件含 `matchId`、`phaseId`、`revision`、`serverTime`。不信任客户端传入的玩家身份，身份从已认证的连接绑定取得。数值范围、所属房间和阶段都由服务端验证。

| 方向 | 消息 | 主要内容与行为 |
|---|---|---|
| HTTP | `GET /health` | 返回进程存活及版本；不暴露房主凭证和玩家令牌。 |
| 客户端→服务端 | `room:join` | 房间码、昵称、颜色；响应玩家 ID、恢复令牌、完整快照；满员明确拒绝参赛，允许观战。 |
| 客户端→服务端 | `session:resume` | 房间码、玩家 ID、恢复令牌；成功后替换旧连接并发完整快照。 |
| 大屏→服务端 | `host:attach` / `host:command` | 管理凭证；命令 `start`、`skip`、`finish`、`reset`，回复成功或明确错误。 |
| 玩家→服务端 | `input` | `seq`、方向向量、跳跃按下/释放状态；仅本连接所绑定的参赛者可发送。连续输入取最新状态，跳跃按键边沿按序号去重，且在网络丢包时有明确补发策略。 |
| 服务端→客户端 | `room:snapshot` | 当前阶段、截止时间、玩家与坐标、当前关卡完整状态、成绩；用于入场及恢复。 |
| 服务端→客户端 | `world:state` | 位置、速度、朝向、服务器 tick 和各玩家已处理输入序号；定期快照，旧包可丢弃。 |
| 服务端→客户端 | `game:event` | 阶段改变、地砖批量变化、拾取、计分、淘汰、结算等；附 revision。结果由权威状态确定，不依赖客户端确认。 |
| 双向 | `time:ping` | 返回服务器时间；客户端估算时钟偏移，只用于显示和动画，不影响裁决。 |

输入示例：`{ "matchId":"m1", "phaseId":4, "seq":123, "move":{"x":0.4,"z":-0.8}, "jumpHeld":true, "jumpPressSeq":7 }`。移动方向裁剪为单位长度；`jumpPressSeq` 单调递增，每次起跳只处理一次，并在后续输入中重复携带，直到服务端确认。输入失联超过 300ms 则方向归零、跳跃释放，避免角色持续跑动。阶段不匹配或序号过旧的输入丢弃，重连后先清空本地待发输入并以服务器确认序号重置。

事件默认可能在断线期间丢失，Socket.IO 的顺序保证不等于送达保证。恢复时以完整快照覆盖本地状态；`revision` 有缺口或事件所属阶段不匹配时主动请求快照。位置快照和连续输入可用 volatile，避免积压过期数据；关键命令使用确认、超时和同一 requestId 重试，服务器在本局缓存处理结果。详见 [消息送达保证](https://socket.io/docs/v4/delivery-guarantees/) 和 [volatile 事件](https://socket.io/docs/v4/emitting-events/)。

## 7. 操作手感和同步

- 服务器以初始 30Hz 固定步长模拟移动、跳跃、落地和接触；客户端以相同步长和共享计算函数对自己立即预测。游戏状态依服务端结果更新。
- 手机每秒约 15 次发送最新方向及重复的跳跃序号；服务器每秒约 10 次发送位置快照。客户端收到自己的权威位置及已处理序号后，从该位置重放尚未确认的输入，小偏差平滑修正，大偏差直接纠正。具体输入历史、采样与服务端消费节奏须在 M0 原型验证，不能仅按帧重放；允许以固定 tick 编号记录历史输入。
- 其他玩家插值显示，初始缓冲约 100–150ms；丢包时短暂保持或有限外推，禁止无限滑行。位置允许过时丢弃，淘汰、计分等以权威事件及快照为准。
- 这不是对手感和吞吐的保证：32 人、弱网、各类手机和 Socket.IO polling 回退都必须实测。将 tick、广播频率和插值缓冲设为配置；必要时合并消息、降低发送频率或画质，不能跳过服务器裁决。

## 8. 六关权威判定与边界

| 关卡 | 服务器做什么 | 关键规则 |
|---|---|---|
| 锦市 | 按接地位置与轨迹确定经过的砖、维护队色及统计 | 60 秒结算。按人数分队；最少队或个人淘汰。同分按达到最终成绩的时间，仍相同按入场顺序。 |
| 灯市 | 选题、锁定时读取服务器角色中心、判区域并结算 | 空中也按水平位置；全错作废；不足晋级数按到正确区域距离补足，同距按入场顺序。最多五题后剩余者晋级。 |
| 七宝市 | 生成物品、判断落地/距离、处理唯一领取并排序 | 同 tick 多人可拾取同一物品时按 `playerId` 稳定排序，仅一人获得；以服务端 tick 为准。到期消失；同分按达到成绩时间，再按入场顺序。 |
| 市散 | 接地踩砖触发定时消失、模拟掉落 | 空中跨越不触发；保护期后脚下砖必须触发。最多 60 秒；同时掉落按通用规则及兜底处理。 |
| 酒市 | 判断近距离拾取粮袋、持有状态、四角交付和补货 | 一次一袋；单物品只能被一人持有；交付后清除持有并只计一次，掉落归还；达标/到时按规则排名补足。 |
| 桂市 | 按服务器可通行台阶、缺口与定时塌落计算运动，检查终点 | 首个有效抵达者夺冠，同 tick 按 `playerId`；超时按进度、高度、入场顺序排序。 |

服务端在固定 tick 内统一处理输入与规则；并发先后以处理顺序和稳定排序为准，不使用客户端时间戳裁决。晋级目标按 [通用规则](../levels/00-common.md) 计算，具体关卡允许按其提前结束规则保留更多人。全员掉落时以最后掉落批次（0.2 秒）为候选；决赛从该批次按终点进度、高度、入场顺序选一人。非决赛若候选不足目标，允许不足目标继续，避免凭空复活；若该批次为空，用本关开始时有资格玩家按入场顺序选一人直接进入结局。该兜底是待试玩确认的具体化，不声称已有设计明确规定。

## 9. 掉线与现场兜底

- 临时断线时保留玩家身份和当前成绩，服务器停止其输入，角色按世界规则继续受重力和地砖影响；不暂停全场。重连成功恢复当前状态；玩家若已淘汰则进入观战。预计最长保留 60 秒，超时或本关结束后无论是否重连都按当时权威结果处理。大厅断线超过 60 秒释放席位；游戏中不移除历史成绩。
- 浏览器刷新可用本地保存的随机恢复令牌恢复，服务端验证并踢掉该身份的旧连接；令牌丢失则以新观众身份进入。房主掉线不暂停时钟，可用管理凭证重连；主持人保管凭证。
- 断线 UI 明确显示重连中、当前状态与失败后观战路径。媒体不阻断计时。服务端异常退出时由现场人员重启、重置和重新扫码；首版不保证进程崩溃恢复。
- 房主按钮可开始、跳关、直接结局、重开。操作写入结构化日志，记录房间、对局、阶段、错误及连接数，不记录令牌。

## 10. 分阶段交付和验证

1. **M0 可联机大厅**：工程启动、手机加入、房主大屏、运动预测与服务器校正、位置广播、断线恢复。两台设备先过，再用模拟客户端加真机测 10 台以上，观察延迟、抖动与 32 客户端基本负载。先确定现场地址能让手机访问。
2. **M1 可走完整局**：阶段机、六个占位关、房主跳关、冠军及重开；验证断线、过期命令、零人和重复消息。无正式素材也能从大厅走到结局。
3. **M2 真实规则**：先网格能力与锦市/市散，再灯市/桂市；再实现拾取及七宝市/酒市。每关覆盖各自并发和人数边界；实际顺序可因联调调整，不改变六关交付范围。
4. **M3 接入和彩排**：按确定的资源接口接入美术、题库、视频、音频；10 台以上 iOS/安卓真机至少两次跑完全局，模拟刷新、弱网、拾取竞争、过场失败和房主跳关。最终现场网络、设备数量及性能阈值需按实测记录。

自动化至少覆盖状态机、结算边界、同物品并发、去重、重连快照、旧阶段输入失效、重开清理；另用模拟客户端验证负载和一致性。自动化不能代替真机与现场网络彩排。

## 12. 扫码入场与过场节奏补充

用户确认：微信只用于扫描房间链接，不接入微信身份授权。玩家打开网页后创建临时身份并进入房间；Demo 仅由我方管理客户端创建房间，普通玩家通过房间链接加入。断线恢复使用游戏自身的会话身份，不依赖微信。

过场建议由服务器统一控制阶段与时间，客户端负责加载和播放表现。服务器公布本次过场标识、开始时间、截止时间及后续阶段；客户端根据服务器时间估算播放进度。播放结束、加载失败或短暂失联均不决定全局推进：未能播放时显示占位卡，截止时按服务器状态切换；房主可跳过，跳过由服务器广播并统一进入下一阶段。迟到或重连客户端先取得完整快照，按当前阶段及剩余时间显示，必要时跳到对应进度或使用占位卡；无法定位播放位置时不应阻塞全场。

建议前一阶段预加载下一段媒体，并在进入前进行有上限的准备检查；超过等待上限仍未就绪的设备使用兜底，不无限等待。手机是否播放视频、媒体版本和具体预加载条件仍以现有冲突文档统一后的决定为准；在确定前只定义统一时间和失败兜底，不冻结具体素材方案。

## 13. 实体与身份简化（2026-10-27 用户补充）

Demo 优先简化，不为未来扩展增加字段。扫码打开后创建本地玩家身份，昵称作为用户可见的身份；浏览器 localStorage 保存昵称、服务端生成的玩家标识及恢复凭证、最近房间标识。重新打开时先尝试恢复该身份及房间；有进行中对局就获取当前快照，直接进入当前游戏或观战画面。身份数据仅在同一设备、同一浏览器及同一站点存储有效；清除数据、更换浏览器或设备后无法依赖它恢复。昵称不作为唯一技术标识，避免两人同名或改名导致串号；允许显示同名，玩家标识与恢复凭证只用于区分和恢复会话。玩家可见身份仍是昵称。

用户有公众号，微信授权登录作为后续可选尝试，权限及域名需实际核验，不阻断匿名扫码入场。扫码、昵称和浏览器恢复是 Demo 的基础路径。

首版核心状态只保留：

- 房间：房间标识、玩家集合、当前对局；管理端创建并控制。
- 玩家：玩家标识、昵称、恢复凭证、连接状态、参赛/淘汰状态、角色位置和运动所需状态。外观及队伍按玩法实际需要保存。
- 对局：对局标识、当前关卡和阶段、阶段截止时间、参赛及结果信息。
- 当前关卡：仅保存本关必要地砖、物品、题目及计分状态；关卡结束保留结果即可。

这些是逻辑分组，不要求分别建表或类。状态保存在单个服务进程的内存中；不引入数据库。局内断线期间世界继续运行，重连后恢复服务器当前结果，包括已淘汰进入观战；服务重启、房间关闭后本地昵称仍可预填，但旧对局无法恢复。第 4 节的实体列表用于解释职责，若与本节首版简化有冲突，以本节为准。
